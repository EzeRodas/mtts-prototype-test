# Implementing a Moon-TTS Engine

This guide explains how to add a new speech engine to Moon-TTS using the out-of-process IPC protocol. Moon-TTS never links engine code: an engine is a separate program (a *worker*) that the app starts and talks to over its stdin/stdout. Any language works, as long as it can read and write bytes on standard input and output.

For the full wire specification see [`IPC-engine-model.md`](../../IPC-engine-model.md). This document is the practical, step-by-step version.

---

## 1. How the host uses an engine

```
 Moon-TTS (host)                                   Your worker process
 ───────────────                                   ───────────────────
 EngineCatalog scans engines/*/engine.json
 user selects "<engineId>/<modelId>"
 spawn <executable>  (cwd = engine folder)  ──────▶ starts, waits on stdin
 GetMetadata                                ──────▶
                                            ◀────── MetadataResponse (engine id, PCM format)
 LoadModel {modelId, modelDirectory, files} ──────▶ load the model files
                                            ◀────── ModelLoaded
 [only if voices.json has no entry for the model]
 ListVoices                                 ──────▶
                                            ◀────── VoicesResponse  → written to voices.json
 ... later, once per sentence ...
 Synthesize {text, voiceId, speed, pitch}   ──────▶
                                            ◀────── AudioChunk (raw PCM) × N
                                            ◀────── EndOfStream
 [user stops speech]  Cancel                ──────▶ stop, then still send EndOfStream
 [model switch / app exit]  close stdin     ──────▶ exit
```

- One worker process serves one loaded model. Switching models starts a new worker and closes the old one's stdin.
- If the worker crashes, Moon-TTS shows an error for that request and starts a fresh worker on the next one (repeating `GetMetadata` and `LoadModel`).
- Everything your worker writes to **stderr** is shown in the Moon-TTS log as `[engine:<id>] ...`. Use it for diagnostics.

## 2. Engine folder layout

Engines are installed into the user's engines folder:

| OS | Engines folder |
| :--- | :--- |
| Linux | `$XDG_DATA_HOME/Moon-TTS/engines/` (default `~/.local/share/Moon-TTS/engines/`) |
| Windows | `%AppData%\Moon-TTS\engines\` |
| macOS | `~/Library/Application Support/Moon-TTS/engines/` |

Each engine gets its own sub folder. The folder name is free; the engine is identified by the `id` in its manifest.

```text
engines/
└── MyEngine/
    ├── engine.json        required: manifest
    ├── voices.json        optional: generated by Moon-TTS if missing
    ├── my-worker          required: the executable named in engine.json
    └── ...                anything else your worker needs (assets, libraries)
```

Model files are **not** stored here. Moon-TTS downloads them into `<models directory>/<engineId>/` (the models directory can be changed by the user in settings) and tells the worker where they are in `LoadModel`.

## 3. Write `engine.json`

```json
{
  "id": "myengine",
  "displayName": "My Engine",
  "description": "Short description shown to users.",
  "version": "1.0.0",
  "executable": "my-worker",
  "models": [
    {
      "id": "small",
      "displayName": "My Engine (Small)",
      "downloadFiles": {
        "small.onnx": "https://example.org/models/small.onnx",
        "small.config.json": "https://example.org/models/small.config.json"
      }
    }
  ]
}
```

| Field | Rules |
| :--- | :--- |
| `id` | Required. Must not contain `/`. Must equal the `engineId` your worker reports in `MetadataResponse`. |
| `displayName` | Shown in the UI. Falls back to `id`. |
| `executable` | Required. Path relative to the engine folder. On Windows `.exe` is appended automatically when the file without extension does not exist, so one manifest works on every OS. On Linux/macOS a script with a shebang (`#!/usr/bin/env python3`) and the executable bit works. |
| `models[].id` | Required. Users address the model as `<engineId>/<modelId>` (e.g. `myengine/small`), or by `<modelId>` alone when it is unambiguous. |
| `models[].languages` | Optional array of language names (e.g. `["English", "Spanish"]`) displayed on the model card in the Engine Management tab. |
| `models[].downloadFiles` | Local file name → download URL. The keys are also the `files` list your worker receives in `LoadModel`. A model with no files (a cloud API, an OS voice, a model bundled in the engine folder) is always considered downloaded. |

The manifest is parsed case-insensitively and accepts comments and trailing commas. An invalid manifest is skipped (with a message in the log) without affecting other engines.

## 4. Voices and `voices.json`

Voices are **not** listed in `engine.json`. You have two options:

1. **Let Moon-TTS generate it (recommended).** Answer `ListVoices`. The first time a model is loaded and `voices.json` has no entry for it, Moon-TTS asks your worker and writes the reply into `voices.json`.
2. **Ship it.** Provide `voices.json` yourself to control names and languages without code changes. If an entry exists for the model, Moon-TTS uses it and does not send `ListVoices`.

```json
{
  "models": {
    "small": [
      { "id": "alice", "name": "Alice", "language": "en-US" },
      { "id": "bob" }
    ]
  }
}
```

`name` and `language` are optional; the UI falls back to the `id`. To force a refresh after changing your voice list, delete the model's entry (or the whole file).

If the user's saved voice is not in the list, Moon-TTS uses the first voice of the model.

## 5. The protocol

### 5.1 Framing

Every message, in both directions, is one frame:

```
offset  size  field
0       2     magic: 0x4D 0x54  ("MT")
2       1     opcode
3       1     flags (send 0, ignore on read)
4       4     payload length, uint32 big-endian (max 32 MB)
8       N     payload
```

Control payloads are UTF-8 JSON with **camelCase** property names. Audio payloads are raw PCM bytes.

### 5.2 Messages your worker must handle

| Request (host → worker) | Your reply | Notes |
| :--- | :--- | :--- |
| `0x10 GetMetadata` (no payload) | `0x11 MetadataResponse` | Sent first, answer within **15 s**. |
| `0x14 LoadModel` (JSON) | `0x15 ModelLoaded` (no payload) or `0xFE Error` | Answer within **2 min**. |
| `0x12 ListVoices` (no payload) | `0x13 VoicesResponse` | Answer within **15 s**. Voices of the loaded model. |
| `0x20 Synthesize` (JSON) | `0x21 AudioChunk` × N, then `0x22 EndOfStream`, or `0xFE Error` | No time limit; stream chunks as soon as they are ready. |
| `0x23 Cancel` (no payload) | *nothing directly* | Stop the active synthesis and finish it with `EndOfStream`. Ignore it when nothing is running. |
| `0x01 Ping` (no payload) | `0x02 Pong` | Liveness check. |
| `0xFF Shutdown` (no payload) | *nothing* | Exit. Also exit when stdin reaches end of file. |
| anything else | `0xFE Error` | e.g. code `unsupported_opcode`. |

**Rules the host relies on**

- **Exactly one terminal frame per request**: the reply opcode, `EndOfStream` (for `Synthesize`), or `Error`. The host sends one request at a time and waits for that terminal frame.
- **stdout carries only frames.** A stray `print` corrupts the channel and the host kills the worker. Send logs to stderr (in C#, call `Console.SetOut(Console.Error)` after opening the raw stdout stream).
- **After `Cancel`, still end the stream.** The host waits up to **5 s** for `EndOfStream`/`Error` after a `Cancel`, then kills the worker.
- If a timeout above is missed, the worker is killed and the request fails.

### 5.3 Payloads

**`MetadataResponse`**
```json
{
  "engineId": "myengine",
  "engineName": "My Engine",
  "version": "1.0.0",
  "author": "You",
  "audioFormat": { "sampleRate": 22050, "channels": 1, "bitDepth": 16, "encoding": "PCM_SIGNED" },
  "supportsStreaming": true,
  "supportsSpeedAdjustment": true,
  "supportsPitchAdjustment": false
}
```
`engineId` must match `engine.json`. `sampleRate`, `channels` and `bitDepth` must be positive, and `bitDepth` a multiple of 8.

> **Use 16-bit PCM.** The host accepts other bit depths in the metadata, but playback (`pw-play`/`paplay` are started with `s16le`) and volume scaling currently assume 16-bit signed little-endian samples. Any sample rate and channel count are supported.

**`LoadModel`**
```json
{ "modelId": "small", "modelDirectory": "/home/me/.local/share/Moon-TTS/models/myengine", "files": ["small.onnx", "small.config.json"] }
```
Build file paths as `modelDirectory` + file name. Reply `Error` (e.g. code `model_not_found`) if something is missing. A new `LoadModel` replaces the previous model.

**`VoicesResponse`**
```json
{ "voices": [ { "id": "alice", "name": "Alice", "language": "en-US" } ] }
```

**`Synthesize`**
```json
{ "text": "Hello world.", "voiceId": "alice", "speed": 1.0, "pitch": 1.0 }
```
The host splits long text into sentences and sends one `Synthesize` per sentence. `speed` is the user's speed setting (1.0 = normal). `pitch` is currently always 1.0.

**`AudioChunk`**: raw PCM in the format you declared. Keep each chunk well under 32 MB; 100–250 ms of audio per chunk gives the lowest latency. Fade the first and last few milliseconds of each sentence to avoid speaker clicks, since the host plays chunks as-is.

**`Error`**
```json
{ "code": "synthesis_failed", "message": "Human readable reason shown to the user." }
```
Codes are free-form strings; the message is shown in the app.

## 6. Writing a worker

### 6.1 In C#

Reference the shared contract project (`MoonTTS.Engine.Protocol`) to get the framing, opcodes, DTOs and an AOT-safe JSON context. The Kokoro worker in `Engines/Kokoro/` is a complete reference; a minimal worker looks like this:

```csharp
using System.Text.Json;
using MoonTTS.Engine.Protocol;

var input = Console.OpenStandardInput();
var output = Console.OpenStandardOutput();
Console.SetOut(Console.Error); /* keep stdout for frames only */

var json = EngineProtocolJsonContext.Default;

while (await EngineIpcProtocol.ReadFrameAsync(input) is { } frame)
{
    switch (frame.Opcode)
    {
        case EngineOpcode.GetMetadata:
            await EngineIpcProtocol.WriteJsonFrameAsync(output, EngineOpcode.MetadataResponse, new EngineMetadataMessage
            {
                EngineId = "myengine",
                EngineName = "My Engine",
                Version = "1.0.0",
                AudioFormat = new EngineAudioFormat { SampleRate = 22050, Channels = 1, BitDepth = 16 },
                SupportsStreaming = true
            }, json.EngineMetadataMessage);
            break;

        case EngineOpcode.LoadModel:
            var load = EngineIpcProtocol.ReadJson(frame, json.LoadModelRequest);
            /* load Path.Combine(load.ModelDirectory, file) for each file in load.Files */
            await EngineIpcProtocol.WriteFrameAsync(output, EngineOpcode.ModelLoaded, ReadOnlyMemory<byte>.Empty);
            break;

        case EngineOpcode.ListVoices:
            await EngineIpcProtocol.WriteJsonFrameAsync(output, EngineOpcode.VoicesResponse,
                new VoicesResponse { Voices = [new VoiceEntry { Id = "alice", Name = "Alice", Language = "en-US" }] },
                json.VoicesResponse);
            break;

        case EngineOpcode.Synthesize:
            var request = EngineIpcProtocol.ReadJson(frame, json.SynthesizeRequest);
            /* foreach (byte[] pcm in MySynthesizer.Stream(request.Text, request.VoiceId, request.Speed))
                   await EngineIpcProtocol.WriteFrameAsync(output, EngineOpcode.AudioChunk, pcm); */
            await EngineIpcProtocol.WriteFrameAsync(output, EngineOpcode.EndOfStream, ReadOnlyMemory<byte>.Empty);
            break;

        case EngineOpcode.Cancel:
            break; /* nothing is running in this synchronous example */

        case EngineOpcode.Shutdown:
            return;

        default:
            await EngineIpcProtocol.WriteJsonFrameAsync(output, EngineOpcode.Error,
                new EngineErrorMessage { Code = "unsupported_opcode", Message = frame.Opcode.ToString() },
                json.EngineErrorMessage);
            break;
    }
}
```

This loop handles requests one at a time, so a `Cancel` is only read after the sentence finishes (the host still waits for `EndOfStream`). To cancel mid-sentence, run synthesis on a background task and keep reading frames, as `Engines/Kokoro/KokoroWorker.cs` does:

- keep a `CancellationTokenSource` for the active job and cancel it on `Cancel`;
- guard stdout with a lock so the request loop and the synthesis task never interleave frames;
- on cancellation, send `EndOfStream`; on failure, send `Error`.

Create the project next to the Kokoro one (`Engines/<Name>/`) and keep it out of `MoonTTS.slnx`, so the app never depends on it. Copy `engine.json` to the output:

```xml
<ItemGroup>
  <ProjectReference Include="..\..\MoonTTS.Engine.Protocol\MoonTTS.Engine.Protocol.csproj" />
  <None Include="engine.json" CopyToOutputDirectory="PreserveNewest" CopyToPublishDirectory="PreserveNewest" />
</ItemGroup>
```

### 6.2 In another language

Implement the framing from section 5.1 and the message table from section 5.2. The Python template in [`IPC-engine-model.md` §5](../../IPC-engine-model.md) is a complete, working starting point that runs unchanged against Moon-TTS. Remember to:

- open stdin/stdout in **binary** mode and flush after every frame;
- read exactly 8 header bytes, then exactly `length` payload bytes;
- write diagnostics to stderr only.

## 7. Install and test

1. **Install.** Put the engine folder into the engines folder, e.g. for a C# worker:
   ```bash
   dotnet publish Engines/MyEngine -o ~/.local/share/Moon-TTS/engines/MyEngine
   ```
2. **Check discovery.** `mtts model list` should list `myengine/<model>`. If it does not, the log explains why the manifest was skipped.
3. **Download the model** (only if it has `downloadFiles`): `mtts model download myengine/small`, or the Engine Management tab in the advanced settings.
4. **Activate it.** `mtts model set myengine/small`. This starts the worker and runs `GetMetadata` + `LoadModel`; any error your worker returns is printed.
5. **Check voices.** `mtts voice list`. On first use this also writes `voices.json` next to your `engine.json`.
6. **Speak.** `mtts play "Hello from my engine"`, or use the main window.

Restart Moon-TTS after installing or removing an engine; the engines folder is scanned once per run.

## 8. Troubleshooting

| Symptom | Likely cause |
| :--- | :--- |
| Engine missing from `mtts model list` | `engine.json` missing, invalid JSON, empty `id`/`executable`, `id` contains `/`, or another engine already uses the same `id`. |
| "Worker executable not found" | The `executable` path in `engine.json` does not point to an existing file. |
| "An error occurred trying to start process ... Permission denied" | (Linux/macOS) the worker file is not executable: `chmod +x <file>`. |
| "Worker reports engine id ... but engine.json declares ..." | `engineId` in `MetadataResponse` differs from the manifest `id`. |
| "did not answer GetMetadata within 15s" | The worker writes nothing, writes to stdout without flushing, or crashes at startup (check the `[engine:<id>]` lines in the log). |
| "Engine IPC frame has invalid magic bytes" | Something other than frames reached stdout (a stray print or a library logging to stdout). |
| Audio sounds like noise or plays at the wrong speed | The PCM you send does not match the declared `audioFormat`, or it is not 16-bit little-endian. |
| Stopping speech takes ~5 s and the worker restarts | The worker does not finish the stream with `EndOfStream` after `Cancel`. |
| Voice names did not update | `voices.json` already has an entry for the model; delete it to regenerate. |

---

## 9. Checklist

- [ ] `engine.json` with a unique `id` (no `/`), an `executable` and at least one model.
- [ ] `MetadataResponse.engineId` equals the manifest `id`; audio is 16-bit PCM.
- [ ] Every request gets exactly one terminal frame (`reply`, `EndOfStream`, or `Error`).
- [ ] `Cancel` ends the active stream with `EndOfStream`.
- [ ] Nothing but frames on stdout; diagnostics on stderr.
- [ ] The worker exits on `Shutdown` and on end of stdin.
- [ ] `mtts model set` and `mtts voice list` work, and `voices.json` was created (or shipped).
